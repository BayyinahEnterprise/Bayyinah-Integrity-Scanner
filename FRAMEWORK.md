# Bayyinah Audit Framework Conformance

This document records how the Bayyinah Integrity Scanner repository
conforms to the Bayyinah Audit Framework v3.0 (Arfeen 2026, sole
authored, hybridised with Fraz Ashraf's engineering approach per
Acknowledgements).

## 1. Pinned framework version

Bayyinah follows Bayyinah Audit Framework v3.0 dated 2026-05-03,
licensed CC BY-NC 4.0. Zenodo DOI to be assigned upon publication.

## 2. Project-specific deviations

The framework is general; some Bayyinah-specific extensions and
deviations are recorded here so a competent stranger reading the
framework alone can reconcile their reading with the substrate.

### v4.1 ZAHIR/BATIN classification rule

Per the framework's general source-layer principle, each finding
carries a `source_layer` of `zahir` (surface, reader-visible) or
`batin` (substrate, structural / hidden). Bayyinah classifies by a
single-walk surface-readability test on the source layer of the
finding, independent of which analyzer module hosts the call. A
finding generated by ZahirTextAnalyzer can be `batin` if the data
it surfaces was extracted from a substrate layer not visible in
default rendering.

### Per-version surface frozenset cadence

Per framework v3 §18.3 (additive-only invariant), the public surface
`bayyinah.__all__` is pinned per version in
`tests/test_public_surface_additive.py`. Every minor and every patch
gets its own `V_X_Y_Z_SURFACE` constant, even when the surface is
unchanged (the new constant aliases the prior one). This pattern was
formalised in v1.2.3 commit 5a73575.

### Five-place documentation pattern

The framework v3 §11 specifies four places for documented
limitations: CHANGELOG, README, fixture, pinning test. Bayyinah
extends to five: each detection mechanism also has an entry in
`bayyinah/mechanisms/registry.py` with its tier and cost class. A
mechanism that exists in the analyzer but not in the registry is a
finding category in its own right.

### Em-dash discipline in user-facing prose

Bayyinah excludes em-dashes from CHANGELOG entries, README content,
finding descriptions, the demo landing page, and similar
user-facing prose. Code comments are exempt; literal grep patterns
matching the em-dash character are also exempt for the discipline-
check command itself. Verified by `grep -c "—"` against changed
prose files at each commit.

### Dependency manifest discipline

New third-party imports go in BOTH `requirements.txt` AND
`pyproject.toml` in the same patch, capped at the current major
version. Adding a dependency to one but not the other is a finding
category surfaced by `tests/test_requirements_dev_sync.py` (added
in v1.2.3).

## 3. Maturity self-assessment

Per framework v3 §23.4 maturity model, Bayyinah is currently at
**Level 4 (Structurally Honest)**:

- Severity rubric (§7) applied uniformly across the audit chain.
- Reproducer-first findings (§4 step 4) on every CHANGELOG entry.
- Four-place documentation pattern enforced (Bayyinah extension:
  five places).
- Pre-flight checklist (§12.1) and five questions (§12.2) applied
  before each commit and at release.
- Validator-by-different-instance protocol (§5.2) in routine use:
  the producer instance (cowork Claude on a prior version) does
  not audit; a fresh Claude instance audits against the public
  artifacts alone.
- Automated gates: 1837+ pytest tests, em-dash sweep, requirements-
  dev sync, public surface additive invariant, mech registry
  consistency, parity against bayyinah_v0 / v01 reference.
- Retirement ledger (this repository's `RETIREMENT_LEDGER.md`)
  maintained across versions.
- Round-trip Shape A / B / C responses (§10.1) on every finding.
- Audit-of-self pattern (§1.2): every round in the Bayyinah audit
  chain is audit-of-self by Bilal Syed Arfeen. Fraz Ashraf is
  acknowledged for the framework's engineering approach (§27),
  not as an auditor on the Bayyinah chain.
